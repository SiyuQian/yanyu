# iOS app execution plan

Status: In Progress. This plan defines a reviewable first-release scope and a native-first iOS architecture. Implementation began on 2026-10-26; no release date is assigned. Estimates are initial engineering effort; re-estimate after the feasibility spike.

## Goal

Deliver an iPhone app for private, local-first speech input. A user opens Yanyu, records speech, reviews and edits the transcript, then copies or shares it to another app. The app keeps transcript history on the device.

The first release is an iOS companion app, not desktop feature parity. Desktop Yanyu is a Tauri 2 application whose recording, OS input, model lifecycle and persistence managers use desktop runtime services. The iOS app will use SwiftUI and Apple audio APIs. A standalone Rust core will hold only logic that can run without Tauri; the desktop app will continue using its Tauri shell. See [architecture](../../ARCHITECTURE.md) and [the current Tauri dependencies](../../src-tauri/Cargo.toml).

## Proposed v1 scope

### Included

- iPhone-first SwiftUI app, built and distributed through TestFlight and the App Store.
- First-run explanation of local processing, microphone permission, and model setup.
- Foreground tap-to-start and tap-to-stop recording with clear recording and processing states.
- On-device transcription using one model selected during the feasibility spike. Chinese and English, including mixed speech, are the initial language requirements.
- Transcript review and editing, with retry and cancel actions where the runtime supports them.
- On-device transcript history with search, copy, share, and delete.
- Minimal settings for language/model selection, appearance, privacy controls, and local transcription text preferences (custom words and filler cleanup).
- English and Simplified Chinese UI, reusing the repository's translation keys and source files. SwiftUI consumes an Apple String Catalog generated from the canonical i18next JSON files; a drift check keeps those generated resources in sync.
- Accessible controls, Dynamic Type-friendly layouts, dark mode, and graceful handling of permission denial, audio interruptions, low storage, and model failures.
- No account requirement. Audio and transcripts remain on-device by default. Raw capture audio is deleted after the transcript is saved. If transcription or saving fails, retain the capture locally with explicit retry and delete actions; never send it off-device.

### Deferred or excluded

- A microphone button that records from a custom keyboard. Apple documents that keyboard extensions do not have microphone access; App Review also prohibits them from launching apps other than Settings. A custom keyboard may be evaluated later for text entry, but it cannot provide desktop-style voice capture. [Keyboard access](https://developer.apple.com/documentation/uikit/configuring-open-access-for-a-custom-keyboard) · [App Review, keyboard extensions](https://developer.apple.com/app-store/review/guidelines/)
- Global hotkeys, system tray, accessibility-driven paste injection, and automatic insertion into another app. The v1 output handoff is copy/share.
- Meetings and computer/system-audio capture. These need a separate mobile product design and feasibility study.
- Desktop model-catalog parity, local LLM polishing, remote post-processing, cloud sync, accounts, and model training/export.
- Background recording. Recording starts only after an explicit action in the foreground. Background execution and interruption behavior can be reconsidered after the core flow is reliable.

## Product and technical decisions

Use these defaults to execute the spike; confirm them before the v1 UI is finalized:

1. **Distribution:** iPhone first. Determine the minimum supported iOS version and whether iPad gets a tailored layout during Phase 0.
2. **Recognition:** local-only for v1, with one verified model. Do not silently send audio or transcripts to a service.
3. **Language bar:** Chinese, English, and mixed Chinese/English speech. If no model meets the quality and performance gate on the target devices, pause and re-scope before building the full UI.
4. **History:** persist editable transcript text locally and mark its Application Support directory as excluded from device backups and CloudKit. Delete raw audio after the transcript is saved; keep it locally with explicit retry/delete actions if transcription or persistence fails.
5. **Handoff:** copy and the native share sheet. Do not promise direct typing into arbitrary third-party apps.
6. **Desktop compatibility:** share stable Rust business logic through a standalone crate. Keep iOS audio capture, app lifecycle, storage paths, and UI native to iOS. Do not make the desktop runtime a dependency of the iOS app.

## User journeys

### First use

1. User sees a short explanation of what stays on-device and why microphone access is needed.
2. User grants or declines microphone access. Declining leaves the app usable for browsing history and settings.
3. User downloads or installs the selected model with visible size, progress, cancellation, retry, and delete controls.
4. App verifies the model and records a short optional sample so the user can confirm the microphone works.

### Dictate and reuse text

1. User opens the recording screen and taps Record.
2. UI clearly shows active capture and elapsed time. User taps Stop.
3. App transcribes locally and exposes progress, cancel, and actionable errors.
4. User reviews and edits the text, then copies it or opens the share sheet.
5. The final text appears in local history and can be revisited, edited, copied, shared, or deleted.

### Recover from failure

Permission denial, call/audio-session interruption, model failure, app suspension, or low storage must not silently lose a completed transcript. Explain whether audio or text was retained, and offer a retry or recovery path when possible.

## Architecture approach

- Build the iOS app as a SwiftUI Xcode target. Use SwiftUI for navigation, recording state, transcript editing, history, accessibility, and the native share sheet.
- Add a standalone Rust crate (proposed name: `yanyu-core`) for reusable transcription/domain logic. It must not depend on Tauri handles, windows, plugins, or event types. Keep desktop app startup, tray, global shortcuts, clipboard injection, and Tauri commands in the existing desktop shell.
- Generate Swift bindings for the Rust API with UniFFI. Keep that API small and typed: model status, transcribe a sandbox file URL, report progress, cancel by job ID, and read/write transcript history. UniFFI supports generated Swift bindings and async APIs; cancellation should be an explicit operation because it is not automatic for an async future. [UniFFI Swift bindings](https://mozilla.github.io/uniffi-rs/latest/swift/overview.html) · [UniFFI async and cancellation](https://mozilla.github.io/uniffi-rs/latest/futures.html)
- Capture audio with `AVAudioEngine` and configure `AVAudioSession` only for the active recording. Store temporary PCM audio in the app sandbox, pass its URL to the Rust API, and remove it when processing finishes. This avoids sending large audio buffers through JavaScript or across many small FFI calls. Apple describes `AVAudioEngine` as its graph-based real-time audio system and requires configuring an input-capable audio session. [AVAudioEngine](https://developer.apple.com/documentation/avfaudio/avaudioengine) · [AVAudioSession](https://developer.apple.com/documentation/avfaudio/avaudiosession)
- During Phase 0, benchmark the current `transcribe-cpp` engine on physical iPhones. Prefer it if it builds and meets quality, latency, memory, thermal, and model-size gates; it preserves more of Yanyu's existing recognition behavior. If it does not pass, compare a Swift/Core ML backend such as WhisperKit behind the same app-level transcription contract. [transcribe.cpp](https://github.com/handy-computer/transcribe.cpp) · [WhisperKit](https://github.com/argmaxinc/argmax-oss-swift)
- The iOS localization path generates an Apple String Catalog and localized microphone-purpose strings from the existing English and Simplified Chinese i18next JSON. These files are generated outputs; the i18next files remain canonical and are checked for drift. This keeps native SwiftUI and avoids a JavaScript UI runtime.
- Store model files and transcript history in the iOS app's Application Support directory. Mark the history directory as excluded from backups and CloudKit. Apple's backup flag is guidance to the system, not an absolute guarantee, so release copy must not promise more than the platform provides. [Backup exclusion](https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup)
- Store one pending raw capture in a dedicated Application Support recovery directory marked as excluded from backups. Remove it after transcript persistence or explicit deletion; on relaunch, offer retry/delete for any unfinished capture.
- Use SwiftUI copy/share APIs for output. No accessibility permission or keyboard extension is part of v1.
- Preserve explicit permission UX and a visible recording state. Apple requires user consent and a clear visual and/or audible indication when recording user input. [App Review, user consent](https://developer.apple.com/app-store/review/guidelines/)

## Acceptance criteria

### Core behavior

- A first-time user can grant microphone access, install the model, record, stop, and obtain an editable transcript without network access after model installation.
- The agreed minimum device completes the initial Chinese, English, and mixed-language evaluation set. Phase 0 records the baseline before setting numeric thresholds; report accuracy and latency separately rather than averaging away language differences.
- The app preserves transcript edits in local history across relaunch. Copy, share, retry, cancel, and delete behave as described.
- Permission denial, interruption, failed model loading, insufficient storage, and cancellation produce understandable recovery states.
- Raw audio is deleted after transcript persistence by default. On transcription or persistence failure, the app retains it in its sandbox and presents retry and delete actions. The audio is never sent off-device.

### Privacy and platform behavior

- No audio or transcript is sent off-device in v1. Verify with network-disabled use after model installation and review all runtime network paths.
- Recording requires a user action and is visibly indicated. The app does not claim continuous/background capture or system-wide keyboard dictation.
- Microphone permission can be denied or revoked without a crash or blocked history access.
- App Store description and privacy disclosures accurately describe local inference, microphone use, and any data retention.

### Release quality

- TestFlight build installs, upgrades, and launches on the supported device/OS matrix.
- No P0/P1 issue remains in recording, transcription, transcript persistence, or output handoff.
- English and Simplified Chinese UI have no missing keys or clipped primary controls.
- VoiceOver can identify and operate the recording, stop, edit, copy/share, and delete controls.
- App Store signing, metadata, privacy answers, screenshots, and review notes are complete.

## Validation plan

During Phase 0, evaluate Chinese, English, and mixed speech, names, numbers, negation, punctuation, and short/long utterances. Compare candidate model accuracy, end-to-end latency, memory pressure, thermal behavior, binary/download size, and airplane-mode behavior on physical devices. Record device, OS, model version, and settings. Keep personal audio local and do not commit it. The generated UniFFI API is linked into the Xcode app; simulator tests verify typed errors and model artifact size/SHA-256 across Swift/Rust. A real model now loads through UniFFI and transcribes public Chinese and English speech on an iPhone simulator, which verifies integration only. It does not establish model quality or physical-device performance.

A supplemental host-only baseline used eight category-selected clips per language from the public FLEURS `cmn_hans_cn/dev` and `en_us/dev` sets. The selection covers short/long clips, numbers, negation, punctuation, and names. CER uses the app's case/whitespace-insensitive, punctuation-preserving character metric:

| Qwen3-ASR 0.6B quant | Mandarin CER (8 clips) | English CER (8 clips) | Correct language detection |
| -------------------- | ---------------------: | --------------------: | -------------------------: |
| Q4_K_M               |         15.8% (50/316) |         3.8% (22/583) |           8/8 per language |
| Q8_0                 |         17.1% (54/316) |         3.4% (20/583) |           8/8 per language |

This deliberately small subset is not a representative benchmark or an acceptance threshold. The Q8 quant has slightly lower English CER and higher Mandarin CER here, so these results do not establish a preferred quant. The FLEURS recordings and catalog-pinned model files stay outside Git. [FLEURS dataset card](https://huggingface.co/datasets/google/fleurs).

A pinned public mixed-speech evaluation uses the speaker-independent `test` and `validation` splits of [ASCEND](https://huggingface.co/datasets/CAiRE/ASCEND), revision `737e9800ae31be9932ba8464c80366559bd28424`. The dataset card identifies the corpus as CC BY-SA 4.0; its authors report written consent for recording and publication in the [paper](https://arxiv.org/abs/2112.06223). From the 1,315-row test split, 358 eligible mixed rows cover 1,473 seconds and two speakers. From the 1,130-row validation split, 191 eligible mixed rows cover 827 seconds and three different speakers. Together, the pinned held-out splits cover 549 utterances, 2,300 seconds, five speakers and four topics. The downloader accepts `--split test` or `--split validation`; audio and references remain outside Git under `/tmp/yanyu-ios-spike/ascend` and `/tmp/yanyu-ios-spike/ascend-validation`. Each downloaded WAV is SHA-256 checked by the on-device batch test.

Mixed error rate (MER) follows the corpus's character/word distinction: NFKC-normalize and case-fold, count each Han character as a token, group non-Han letters and digits into word tokens, and ignore punctuation and whitespace. This host-only result is not a model acceptance threshold:

| Split                              | Model quant |                  MER | Outputs with both scripts | Median host RTF |
| ---------------------------------- | ----------- | -------------------: | ------------------------: | --------------: |
| Test (358 clips, 2 speakers)       | Q4_K_M      |   12.22% (643/5,260) |           278/358 (77.7%) |           0.058 |
| Test (358 clips, 2 speakers)       | Q8_0        |   11.84% (623/5,260) |           290/358 (81.0%) |           0.060 |
| Validation (191 clips, 3 speakers) | Q4_K_M      |   15.31% (460/3,004) |           135/191 (70.7%) |           0.058 |
| Validation (191 clips, 3 speakers) | Q8_0        |   14.75% (443/3,004) |           133/191 (69.6%) |           0.060 |
| Combined (549 clips, 5 speakers)   | Q4_K_M      | 13.35% (1,103/8,264) |           413/549 (75.2%) |               — |
| Combined (549 clips, 5 speakers)   | Q8_0        | 12.90% (1,066/8,264) |           423/549 (77.0%) |               — |

Across these five speakers, Q8_0 scored 0.45 percentage points lower on weighted MER and retained both scripts in 10 more clips, while its model file is about 261 MB larger. The corpus remains small and accent-specific; host timing and five speakers cannot select an engine or quantization for iPhone release. [ASCEND license](https://creativecommons.org/licenses/by-sa/4.0/).

The Q4_K_M batch also completed on the iPhone 17 simulator (model identifier `iPhone18,3`, iOS 27.0) for the test split: MER was 12.32% (648/5,260), both scripts appeared in 280/358 outputs (78.2%), core processing took 72.4 seconds (RTF 0.049), and model loading took 226 ms. The test sampled a 1.24 GB peak physical-memory footprint, observed only nominal thermal state, and recorded no failed samples. The validation split also passed end to end for both Q4_K_M and Q8_0: Q4_K_M scored 14.91% MER (447/2,997), retained both scripts in 133/191 outputs, processed 826.7 seconds of audio in 40.6 seconds, loaded in 246 ms and reached a 1.27 GB sampled peak; Q8_0 scored 14.35% (430/2,997), retained both scripts in 134/191, processed the batch in 37.7 seconds, loaded in 286 ms and reached a 1.62 GB sampled peak. Both runs had zero failed samples and nominal thermal state. These runs validate the Swift/UniFFI/Rust path and harness. Simulator resource readings do not estimate physical-iPhone limits; transcript-free reports remain outside Git.

The localization generator has unit coverage and a drift check. Validate actual English/Simplified Chinese display, interpolation, accessibility labels, and VoiceOver in the app before release. Model artifacts are checked against the supplied manifest's SHA-256 values; before enabling a production remote catalog, authenticate the manifest with a trusted signature or an app-bundled digest and review the approved download origins.

The DEBUG-only evaluation harness imports one local WAV at a time and exports a report with the fixture/model names, sizes and SHA-256 hashes, device identifier, OS version, audio duration, core processing duration, real-time factor, and recognized text. The test target also has an opt-in ASCEND batch run: stage either pinned held-out split's manifest and hashed WAVs, plus one `model.gguf`, in `Documents/ascend-evaluation`, then run `testASCENDMixedTestSetWithLocalModel`. It reports MER, output script retention, language detections, model-load and batch time, sampled physical memory, and thermal states to `evaluation-report.json` without writing transcripts to the report. During evaluation the resource monitor samples every 100 ms; sampling can miss short memory peaks, and simulator measurements do not establish phone limits. The manual single-file path uses the app's character error rate (CER), measured over Unicode grapheme clusters while ignoring whitespace and letter case and preserving punctuation. Neither metric sets an acceptance threshold or replaces human review.

During Phases 2–4, validate microphone permission flows, interruptions (calls, route changes, app backgrounding), low-storage recovery, model download cancellation/resume, relaunch during processing, text edit persistence, offline behavior, VoiceOver, and localization. Use simulators for UI iteration but physical devices for audio, inference, thermal, and memory claims.
